二、稳定性/可靠性风险

2.1 严重 OkHttpClient 无复用 — 连接泄漏
文件: RouterAgent.java 第 742 行，TrustAllCertOkHttpClient.java
// 每次 executeAction 都创建新实例
OkHttpClient okHttpClient = TrustAllCertOkHttpClient.getTrustAllCertOkHttpClient(cookieStore);
每次请求创建新 OkHttpClient → 新的连接池和线程池。高频调用下会:
- 耗尽系统文件描述符（TCP 连接不复用）
- 线程数暴涨
- TIME_WAIT 堆积
建议: OkHttpClient 改为实例变量，构造时创建一次，整个生命周期复用。

我的意见：上层业务平台可能同时对接多个ikuai节点，如按照你的方案修复，是否会出现不同节点用同一个OkHttpClient实例？



2.2 严重 Response Body 未正确关闭
文件: RouterAgent.java 第 206-208 行 (login 方法)
Response response = call.execute();
String response_string = response.body().string();
// response 未 close
login() 方法中 Response 未关闭。response.body().string() 虽然会消费流，但 OkHttp 文档明确要求 Response 必须 close（或在 try-with-resources 中使用），否则底层连接不归还连接池。
executeAction() 中虽有 response.close() (第 769 行)，但如果 response.body().string() 抛异常，close 不会执行。
建议: 统一使用 try-with-resources:
try (Response response = call.execute()) {
    return response.body().string();
}

三、性能问题
3.1 中等 端口查找算法 O(P×N) 复杂度
文件: IkuaiRouter.java 第 256-311 行
for (int currentPort = portbegin; currentPort <= portend; currentPort++) {
    for (NetMapping netMapping : netMappingList) {
        // ...逐条解析 wan_port 字段
    }
}
findAvailableNetMappingWanPort 对每个候选端口都遍历全部端口映射规则。如果端口范围为 30000-65535（35535个）、规则数为 500，则最坏情况需要 17,767,500 次迭代。
建议: 预先将所有已占用端口解析为 HashSet<Integer>，查找时 O(1) 判断:
Set<Integer> usedPorts = new HashSet<>();
for (NetMapping mapping : netMappingList) {
    parsePortsInto(usedPorts, mapping);
}
for (int port = portbegin; port <= portend; port++) {
    if (!usedPorts.contains(port)) return port;
}

我的意见：端口查找逻辑很复杂，参数有 接口、开始端口、结束端口，最终目的是：返回一个没有被任何接口映射出去的端口号。遍历所有端口映射条目，只要有以下情况就算不可用：1、接口列表中包含入参接口；2、外部端口和当前检查端口号相同或者包含。这些逻辑必须保持。按照你的做法，具体怎么改？



3.2 中等 IP 查找四层嵌套循环
文件: IkuaiRouter.java 第 520-573 行
for (int A = ...; ...) {
    for (int B = ...; ...) {
        for (int C = ...; ...) {
            for (int D = ...; ...) {
                for (DHCPHost dhcpHost : dhcpHostList) { ... }
                for (DHCPStatic dhcpStatic : dhcpStaticList) { ... }
            }
        }
    }
}
对每个 IP 地址都线性扫描 DHCPHost 和 DHCPStatic 列表，时间复杂度 O(IP数 × (Host数 + Static数))。/24 子网有 254 个 IP，若 Host+Static 共 200 条，则约 50,000 次比较。
建议: 预先将已用 IP 放入 HashSet<String>，内层判断改为 contains():
Set<String> usedIps = new HashSet<>();
dhcpHostList.forEach(h -> usedIps.add(h.getIp_addr()));
dhcpStaticList.forEach(s -> usedIps.add(s.getIp_addr()));

我的建议：可以按照你的方案修改，但是必须保持逻辑正确。



3.3 低 分页硬编码 limit=0,1000

我的意见：按照你的方案做，或许可以再细化一些，区分更多类型的Exception（如果有必要的话）。

private <T> T parseData(ResponseShow response, String dataKey, TypeReference<T> type) throws Exception {

    return objectMapper.readValue(targetNode.toString(), type);

五、架构设计问题
5.1 中等 无会话自动续期/重连
Session 过期后，所有后续请求直接抛异常。调用方需自行捕获异常并重新登录。
建议: 在 executeAction 中检测 Result == 10014 时自动重新登录并重试一次:
if (responseBase.isAuthFail()) {
    login();  // 自动重新登录
    // 重试一次请求
}

我的意见：上层业务系统会将sesskey缓存到redis，过期时间和ikuai凭证有效期相同，redis缓存过期后，会自动reLogin获取新的sesskey存入redis。有上层业务逻辑兜底，这个问题不是很大。检查一下SDK中是否有探测sesskey是否有效的方法？（该事项后续再处理，可以先讨论方案）


5.2 中等 增删改无并发保护
addNetMapping → getNetMappingList → 判断 → 写入，整个流程非原子操作。并发场景下可能出现同一端口被分配给两个不同规则。
建议: 高并发场景下提供乐观锁或应用层加锁机制。

加锁机制具体如何实现？给出一个方案。


5.3 低 查询结果无缓存
每次 isWanPortInUse 或 findAvailableXxx 都会触发完整的 HTTP 请求获取全量数据。在批量操作场景（如 idTest 中循环 10 次添加端口映射），可能在 1 秒内重复请求同一数据集 10 次。
建议: 提供可选的短时缓存（TTL 可配置），或 findAvailableXxx 接受已获取的列表作为参数。

我的意见：如果增加缓存，则极端情况还是可能出现例如同一个端口被分配给2个规则的情况，因此重新请求全量数据是必须的。


5.4 低 批量操作无事务性
downNetMappingByLanIp 循环禁用多条规则，如果中间某条失败，前面已执行的不会回滚：
public boolean downNetMappingByLanIp(String lanip) throws Exception {

        }
    }
    return true;
}
建议: 文档明确说明非事务性语义；或返回操作结果列表供调用方判断。


我的意见： 循环内部try-catch，记录规则操作结果返回
